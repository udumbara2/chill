# Self-Improve · 程序自改进审查

> 核心原则：**只读分析，不修改代码。发现问题 → 排序呈现 → 用户选择 → self-iterate 实施。**

本技能是 chill 的自我审查机制，系统性分析程序表现和代码质量，按优先级输出可执行的功能项清单。

## 边界说明

- 本技能只做分析和建议，**绝不修改代码**。
- 发现改进点后，用户可选择是否进入 self-iterate 实施。
- 与 self-diagnose 的区别：self-diagnose 修 bug，self-improve 找改进方向。
- 同时支持自然语言触发（"帮我反省一下"）和快捷命令（`/improve`）。

## 提取标准（收录判据）

本技能与自动攒料（`improvementProposer`）共用同一套提取标准，**单一事实源**为 `core/src/services/ImprovementProposalManager.ts` 导出的常量 `IMPROVEMENT_EXTRACTION_STANDARD`（内容如下）。只收录「从用户使用角度看的、能靠改 chill 自身实现的、需要改变的功能」（改进 / 添加 / 删除 三类）；**不收录**「让模型换个说法」类规训条目（措辞、语气、格式、风格、回复精简度、结论先后等）。

> 【提取标准】
> 1. 视角 —— 只从用户使用角度出发：描述用户遇到的不便与期望，不写代码落点、不写实现方式。
> 2. 杠杆 —— 只收「改 chill 自身能实现」的：代码 / 架构 / 设计 / 机制 / 提示词（含技能文档与指令文案）。
> 3. 边界 —— 不收「让模型换个说法」类：措辞、语气、格式、风格、回复精简度、结论先后一律不算；不要用提示词去约束模型的表达自由。修补提示词的功能缺陷（指令遗漏、自相矛盾、工具描述不准导致模型用错或做不到）算改进；要求模型改变表达方式不算。
> 4. 判据 —— 问一句「这条是让 chill 这个产品更好用，还是只是让模型更合我意？」后者不收。
>
> 【三类改变】
> - 改进：现有功能有缺陷或不顺手，应当改好
> - 添加：用户需要一个现在没有的能力，应当补上
> - 删除：有功能多余 / 误导 / 添乱，应当去掉

第四步归档、以及代码静态审查产出条目时，一律按本判据过滤。

## 分析流程

### 第一步：明确范围

询问用户关注范围：
- 无指定 → 全域审查（所有输入源）
- 有指定 → 按指定范围聚焦（如"只看代码质量""只看架构"）

### 第二步：收集发现

先读 `~/.chill/improvement-proposals.md` 获取 Layer 1 自动累积的发现（"待确认"区），再按需从以下输入源收集证据：

**代码静态审查（五维框架）**：
1. **架构**：包边界清晰度、循环依赖、抽象层合理性、模块职责单一性
2. **代码质量**：重复代码、过长函数、硬编码值、不一致模式、TODO/FIXME 分布
3. **健壮性**：错误处理完整性、边界条件处理、资源清理（worker/文件句柄/定时器）
4. **性能**：同步阻塞、重复计算/IO、大对象拷贝、工具调用链路过长
5. **用户体验**：提示信息清晰度、错误消息可操作性、命令一致性、危险操作门槛

**其他输入源**：
- 会话历史：用 search_sessions 搜索 abort、用户纠正、模型绕弯模式
- 自迭代档案：读 `<chill-archive绝对路径>/iteration-v*.json` 找失败模式和重复目标（绝对路径见系统提示的「当前运行状态」）
- 版本回滚历史：用户回滚/删除的版本说明方向有问题
- 长期记忆：读 `~/.chill/memory/` 中 feedback 类型，用户明确表达的偏好
- AGENTS.md vs 实际代码：对照 CLI/UI 独立运行、TUI 内聚、无跨包越界等原则
- Skill 系统：检查 skill description 是否精准、是否很少触发
- 磁盘/资源：检查 sessions/versions 目录大小

### 第三步：评估影响 + 难度，排出优先级

影响和难度定义：

| 维度 | 定义 |
|------|------|
| 高影响 | 影响核心功能、日常使用效率、程序稳定性 |
| 低影响 | 边缘场景、锦上添花、影响范围小 |
| 低难度 | 改几行代码、调整配置、修改 prompt |
| 中难度 | 涉及多个文件、需要测试验证 |
| 高难度 | 涉及架构调整、跨包改动、需要重设计 |

优先级矩阵：

难度 ↓ / 影响 → | 高影响 | 低影响
---|---|---
**低/中难度** | P0 | P2
**高难度** | P1 | P3

### 第四步：归档新发现

审查产出的 P0-P3 清单中，**所有未被用户明确关闭的条目，必须自动追加到 `~/.chill/improvement-proposals.md` 的「待确认」区**。不允许只在对话中口头讨论，必须落盘。

用 replace_content 在「待确认」标题后插入新条目（按 proposals.md 已有的格式）。

### 第五步：统一决策

审查和归档完成后，调用 `manage_improvements` 工具（仅 managed 布局下可用）让用户批量决策。调用时不传 decisions 参数，工具将自动展示待确认列表并收集用户回复：

```
manage_improvements({})
```

工具将展示**簇级紧凑概览**（digest 摘要行 + 按活跃度排序的问题簇清单，每簇一行：簇名/条数/近增/主难度）并携带 Top 簇快捷选项（TUI ↑↓ 菜单 / 桌面弹窗按钮 / 手机提问卡按钮自动点亮）。逐条阅读请引导用户用 `/improve` 面板（TUI/GUI 改进面板，直读账本）。决策语法：

- `y C26`（**整簇确认**，簇编号见簇名前缀）· `s C26`（跳过）· `del C26`（删除整簇，可恢复）；单条编号裁决在 /improve 面板
- `确认 C26 簇` / `跳过 C26`（友好短语，与各端按钮文案一致）
- `all` / `s all` / `del all`（全部确认 / 全部跳过 / 全部删除）
- **未提及的条目默认保留待确认**，不会静默删除（30 天未决策由面板打开时自动归档进「已关闭」区，可恢复）

用户也可以随时用 `/improve` 命令自行决策（TUI 单键面板 / CLI 文本循环，秒开免审查）；`/improve review` 才触发本技能的完整审查。

**npm 模式下工具不可用**：直接在对话中口头展示待确认列表，用户口头回复决策后，用 replace_content 逐条更新文件（回退方案）。

### 审查收尾

提示用户：
> 以上还有 P0/P1 项未决策，你想逐一处理还是先做哪一个？也可以随时让我对已确认条目启动 self-iterate。若有新的改进想法，我可以帮你归档到 proposals.md。
